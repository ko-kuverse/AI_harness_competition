# 智训引擎 Harness 最小闭环

一条按批到达的带标签数据流进来，Harness 对每一批依次做漂移检测、回滚核对、归因、受控实验、门控，然后交出本批决策（promote、hold 或 rollback）和所选模型，再去取下一批。全程无人干预，只用 CPU 和 NumPy。工业模型的训练、保存、加载全部调用官方基线包里的 `baselines.model.Model`，基线包代码没有改动。

目前在 C 赛道（涡扇发动机 RUL）的公开数据上跑通。任务类型从检查点元数据读取，分类任务走同一套流程，只在合成数据上验证过。

## 运行

```sh
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
export PYTHONDONTWRITEBYTECODE=1

# 1. 用公开数据生成一条本地漂移流（regime 或 sensor-aging）
.venv/bin/python -m harness simulate --public cpu-c-guide-20261110-v1/public \
    --out work/sim --scenario sensor-aging --seed 59

# 2. 跑闭环。输出目录必须是新的；指向已有目录时从上次决策过的批次之后续跑
.venv/bin/python -m harness run --stream work/sim/stream --workdir work/run

# 3. 用 Harness 没见过的留出数据给每批决策打分
.venv/bin/python -m harness score --workdir work/run --hidden work/sim/hidden

# 测试（合成数据，约 4 秒）
.venv/bin/python -m unittest discover -s tests
```

常用参数：`--config configs/harness.json`（全部阈值与预算，字段说明见 `config.py`）、`--baseline-dir`、`--checkpoint`、`--swanlab-mode offline|online|local|disabled`、`--project`、`--llm`。

镜像：`docker build -t zhixun-harness .`，运行时把批次流挂到 `/data/stream`、输出挂到 `/work`。

## 每一批做什么

数据划分是后面各步的前提。本批训练部分按设备 8:2 分成拟合集和选型集；本批验证部分作为门控集，只在门控时用一次。平台不单给验证集时，从训练部分按设备划出四分之一作门控集。平台随批重发的历史样本按 id 去重。

| 步骤 | 做法 | 代码 |
| --- | --- | --- |
| 漂移检测 | 输入：逐特征对参考窗口算分位数分箱 PSI 与 KS，告警线取 max(0.25, 2 × 参考窗口内按设备折半的 PSI)，至少 2 个特征越线才判漂移。目标：标签分布 PSI。性能：在线模型在新批次上的主指标，自助法下界超过锚点上界的 1.05 倍判劣化。参考窗口是该版本上线的那一批；静态基线在拿到第一批之前没有样本可比，先用检查点里的均值、标准差做高斯近似 | `drift.py` |
| 回滚守卫 | 新批次到达后先核对在线模型，对手是静态基线和最近 3 个上线过的版本，数据用本批训练部分（已有版本都没见过）。比静态基线差（点估计）就退回静态基线；比其他旧版本差 2% 以上且显著才退回 | `gate.rollback_guard` |
| 归因 | 给出漂移类型（输入漂移是否伤及精度、映射变化、目标分布变化）、程度、越线特征及其偏移量，以及误差在目标值低、中、高三段的分布 | `drift.diagnose` |
| 受控实验 | 触发条件：检出漂移、刚回滚、前 3 轮例行、上一批刚上线。对照是不更新的在线模型，基准试验用当前策略，其余试验各只改一个因素（学习率乘或除以 2.5；数据范围 recent、replay、cumulative）。每个试验从在线模型的检查点续训，逐轮在选型集上评估并保留最好的一轮。每条假设由选型集上的配对自助法给出 supported、refuted 或 inconclusive | `experiment.py` |
| 策略自改进 | 假设获得支持的变体，其取值写进策略，成为下一轮的基准；学习率的试探方向按上次结果保持或反转。各试验臂的累计战绩记在 `state.json` 和报告里 | `experiment.update_policy` |
| 门控 | 选型集上最好的试验（成绩相差 2% 以内视为并列，取历史批次上遗忘更少的）进入门控。拦截项：检查点重载后预测一致且步数增加；门控集不少于 10 台设备；相对在线模型增益不低于 3% 且配对自助法单侧 95% 显著；不差于静态基线；回归任务的非对称误差（NASA 评分的指数项均值）劣化不超过 2%。历史批次上的遗忘幅度是提示项，写进记录但不拦截 | `gate.promotion_gate` |
| 决策与发布 | 写 `decisions/<批次>.json`，把所选模型放到 `production/`，交回决策后才能读下一批。处理某批时出任何异常，保持在线模型并照常交出 hold | `loop.py`、`registry.py` |

单批实验预算：2 到 4 个试验，墙钟 300 秒，训练行数上限 60000，每个试验默认 20 轮（上限 40），选型集连续 5 轮不再变好即停。

遗忘只作提示的理由：流上的分布未必回到过去，为保住旧批次而拒绝修复当前分布得不偿失。旧版本都留在注册表里，旧工况重现时由回滚守卫切回去。

## 输出目录

```
<workdir>/
  config.json              本次运行的完整配置
  state.json               游标、在线版本、策略、各试验臂统计、大模型用量
  registry/index.json      版本血缘：父版本、摘要、上线批次、对应试验
  registry/vN/             checkpoint.npz 与参考窗口 reference.npz；v0 是官方静态基线
  trials/bXXX-tK-<臂>/     每个试验的 checkpoint.npz、training.json、history.jsonl
  decisions/<批次>.json    本批决策和全部证据（漂移、归因、试验、门控各项数值）
  production/              当前上线模型 checkpoint.npz 与 DECISION.json
  records/events.jsonl     本地台账，内容与 SwanLab 记录一一对应
  swanlog/                 SwanLab 离线记录
  report.md  summary.json  运行报告
  score.md   score.json    留出数据评分（运行 score 之后才有）
```

`production/checkpoint.npz` 可以直接交给官方 `python -m baselines.predict --checkpoint`。

## SwanLab 记录

记录的是工业模型的训练与迭代过程，分三类实验：

- 试验（job_type=trial，每个试验一个）。配置里有假设、改动的因素、超参数、父版本及其摘要、训练矩阵摘要、官方训练代码各文件摘要、随机种子；指标逐轮记录 `train/loss`、`select/*`、`retention/<主指标>`，结束时记录 `final/*`。
- 批次决策（job_type=decision，每批一个）。`drift/*`、`stream/*`（到达时在线模型与静态基线、决策后模型）、`decision/*`、`gate/*`、`cost/*`，配置里有决策理由、越线特征、门控各项是否通过。
- 流汇总（stream-summary）。按批次回放整条流的指标、决策与累计耗时。

默认 `offline`，记录落在 `<workdir>/swanlog/`。评测环境没有外网，事后在能联网的机器上执行 `swanlab login` 和 `swanlab sync <workdir>/swanlog/run-* -w <空间> -p <项目>` 上传。设置了 `SWANLAB_API_KEY` 时可用 `--swanlab-mode online` 直接上传；没有密钥时自动退回 offline。SwanLab 未安装或中途出错时只写本地台账，闭环不中断。

## 接入评测平台时要改的地方

1. 批次流。`data.DirectoryStream` 假设每个子目录是一批，内含 `train.jsonl` 和 `validation.jsonl`。平台 SDK 发布后，换成同样提供 `next_batch()` 和 `submit_decision()` 的适配器即可，主循环不用动。
2. 驱动模型。`--llm` 打开大模型规划器，环境变量 `PYTRIO_BASE_URL`（OpenAI 兼容接口根地址）、`PYTRIO_MODEL`、`PYTRIO_API_KEY`。大模型拿到的是诊断结论、历史试验和动作空间，只负责提出基准之外的对照试验；提议先约束到动作空间内，越界的丢弃；调用失败时退回规则规划。思考模式开关等服务端参数写在配置的 `llm.extra_body` 里。
3. 实验记录字段。《实验记录规范》发布后，对照它调整 `experiment.run_trial` 和 `loop._commit` 里写入 SwanLab 的键名。

## 本地验证结果

模拟器把公开数据切成 8 批。每批训练部分取自公开训练集，验证部分取自公开验证集，另从公开训练集整台划出约 15% 的设备作留出评分数据，Harness 读不到。两个场景：

- `regime`：按 FD001、FD003、FD002、FD004 的顺序出批，工况数和故障模式随子集切换。
- `sensor-aging`：各子集混合后平稳出批，第 3 到 6 批给 sensors[1..3] 叠加 0.5σ、1.0σ、1.5σ、2.0σ 的偏移，第 7、8 批偏移归零（换上新传感器）。

评分方式：每批用该批决策选中的模型，在同一阶段的留出样本上算 RMSE，与静态基线比较，再对 8 批取平均。

| 场景 | 种子 | 上线 / 保持 / 回滚 | 试验数 | 留出数据逐批平均增益 | 最差一批 | 不差于静态基线的批次 |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| regime | 7、11、23、31、47、59、61 | 0 / 8 / 0（七个种子相同） | 26–29 | 0.0% | 0.0% | 8/8 |
| sensor-aging | 7 | 2 / 5 / 1 | 20 | +29.7% | 0.0% | 8/8 |
| sensor-aging | 11 | 3 / 4 / 1 | 23 | +31.9% | −6.5% | 7/8 |
| sensor-aging | 23 | 2 / 5 / 1 | 20 | +30.3% | 0.0% | 8/8 |
| sensor-aging | 31 | 2 / 5 / 1 | 23 | +30.2% | 0.0% | 8/8 |
| sensor-aging | 47 | 1 / 6 / 1 | 23 | +30.8% | −2.3% | 7/8 |
| sensor-aging | 59 | 1 / 6 / 1 | 20 | +29.3% | 0.0% | 8/8 |
| sensor-aging | 61 | 2 / 5 / 1 | 20 | +30.4% | 0.0% | 8/8 |

读这张表需要知道三件事。

第一，`regime` 场景下 Harness 每批都做了实验，却一次也没有上线，结果与静态基线完全相同。原因在模型层：官方的 833 参数逐点 MLP 从基线续训，能拿到的增益很小。另做过一次摸底（FD001、FD003、FD002 各取半个子集，学习率 0.001 到 0.01，批大小 64 和 256，训练 100 轮），即使事后在验证集上挑最好的一轮，RMSE 也只比基线低 2% 到 8.5%，相邻检查点之间还有几个百分点的起伏。同一个候选换一批设备评估，结论可能反转：开发过程中种子 31 的一次试跑里，某候选在 8 台设备的门控集上好 11.8%，在 5 台设备的留出集上差 9.4%。门控因此要求门控集至少 10 台设备、增益至少 3%。FD001 和 FD003 的半子集批次验证部分只有 7 到 8 台设备，全部卡在设备数要求上（七个种子共 28 个这样的批次，其中 3 个批次的候选只差这一项）；FD002 和 FD004 的批次有 18 到 20 台设备，候选在门控集上的增益落在 −2.5% 到 +2.3% 之间，达不到增益要求。要在这类流上拿到正增益，得先改特征或模型结构（时间窗、按工况标准化等）。

第二，`sensor-aging` 里低于静态基线的两批（种子 11 和种子 47 的第 7 批）都是传感器更换后的第一批。当时的在线模型是适应了偏移的版本，回滚守卫只看本批训练部分，它在那上面比静态基线略好（RMSE 56.87 对 57.61，53.85 对 54.16），于是没有回滚，到第 8 批才退回静态基线；而在留出样本上它差了 6.5% 和 2.3%。每批留出样本只有 9 到 10 台设备，这个差值有多少是抽样波动，现有数据判断不了。

第三，门控的两个默认值（最小相对增益 3%、门控集至少 10 台设备）和对静态基线的回滚规则，是看过种子 7、11、23、31、47 的留出结果之后定的。种子 59 和 61 没有参与任何设计取舍，可以当作独立检验。

`sensor-aging` 场景下检测结果与注入的真值一致：七个种子里凡是相对参考窗口存在偏移的批次，越线特征都恰好是 sensors[1]、sensors[2]、sensors[3]，没有多报也没有漏报。种子 59 的两条流各独立跑了两遍，各批决策、所选模型摘要、全部试验检查点摘要完全相同。

资源占用（4 核 aarch64 Linux 虚拟机，单线程 BLAS）：8 批的一条流墙钟约 11 到 16 秒，其中训练 3 到 6 秒，其余主要是解析 JSONL 和写记录；峰值内存 190 到 230 MB。

`runs/` 下保存了种子 59 两个场景的输出（不含参考窗口文件）。SwanLab 离线记录 `swanlog/` 自带忽略全部内容的 `.gitignore`，不进版本库，只在本地副本里，可以直接 `swanlab sync`；`records/events.jsonl` 是同一份记录的台账。

## 尚未验证与已知局限

- 镜像没有实际构建过。
- SwanLab 只验证了 offline 落盘，没有执行过在线上传和 `swanlab sync`。
- 大模型规划器只对本地模拟的 OpenAI 兼容服务测试过，没有连过 PyTRiO。默认运行走规则规划。
- 平台的批次投递格式和《实验记录规范》都还没拿到，`DirectoryStream` 与记录字段是按赛题说明会的描述做的假设。
- A、B 赛道没有数据，分类路径只有合成数据上的测试。分类任务门控用错误率，A 赛道的官方主指标是 Macro-F1，两者不等价。
- 样本 id 不符合 `<设备>_c<循环>` 格式时，自助法改用连续 64 行分块作重采样单位，置信区间会偏窄，门控集设备数的检查也随之失效。换数据时先改配置里的 `group_pattern`。
- 试验只调学习率、批大小、轮数和训练数据范围，不改网络结构和输入特征。
- 漂移持续存在而候选一直过不了门控时，每批都会重做一轮实验，没有退避机制。
- 回滚发生在新批次到达之后。按到达时刻（更新之前）评分的话，分布突变的那一批会吃到旧模型的误差。
